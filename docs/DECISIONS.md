# Decisions and deterministic manifest

## The manifest (`meta` in the index)

These decisions are **stored in the `.db`** so two machines produce the same index and so we know when to reindex:

| Key | v1 value | Why |
| --- | --- | --- |
| `schema_version` | 1 | migrate/reindex if it changes. |
| `git_version` | from env | rename detection (`-M`) is heuristic; pinning it makes results comparable. |
| `first_parent` | **false** | corrected empirically: `--first-parent` hid branch commits that do change files (undercount). |
| `no_merges` | true | count all real (non-merge) work, wherever it lives. |
| `mailmap_used` | true | author identities. |
| `bulk_threshold` | 50 | commits touching more files are excluded from coupling. |
| `last_sha` | — | watermark for incremental `sync`. |
| `repo_path` | abs path | so `sync` and per-repo config work without an argument. |

## Decision log (condensed ADR)

1. **One SQLite file, not Memgraph/Qdrant.** Personal scale; a portable `.db` beats distributed infra. **Firm.**
2. **Never embed diffs.** They embed poorly and cost; only NL text (messages/PRs), and only in v2. **Firm.**
3. **Stream `git log`, not libgit2.** git already handles the edge cases; constant RAM. **Firm.**
4. **Symbol history: cheap yes, AST no** *(revised 2026-09-20)*. Symbol-level metrics are IN scope **only via the hunk's function name** (git's `@@ … @@ <funcname>`, with chrono's own `xfuncname` regex so results don't depend on the user's git version). A symbol is another `Touch` with `entity_type="symbol"` (`file#func`); opt-in (`init --symbols`), off by default (the cost is `init` time from `-p`, not binary size). **Still permanently out of scope:** parsing the AST of every blob in history, mass `git blame`, call graphs / function renames / complexity, predicted "regression risk". tree-sitter, if ever, is an opt-in Cargo feature for a few languages, only if measured misattribution warrants it. See `DESIGN-GENERAL-CORE.md §7 (S0–S3)`.
5. **"Most common bugs" = relational (where) + keyword taxonomy (what kind).** Token-frequency clustering was too weak; a configurable `bug_categories` map yields semantic categories (memory-safety, crash, network…). *(Recalibrated after a real opencode test.)*
6. **Classifier: rules (Level 0) in v1.** A trained local classifier and Jev need a labeled dataset + eval metric first; v2.
7. **`serve` is a second product** → scaling phase, not v1.
8. **Ports only where 2+ adapters will exist:** Source, Tracker, Classifier. Store/Embedder go direct for now.
9. **Go for v1** (delivery speed; Rust's memory argument was about the deferred service).
10. **Sized for ~500k commits.** File sizes computed only for the top ~4000 most-changed files (fast on huge repos; Bun = 17,678 commits).
11. **Positioning by capabilities, not "99% fewer tokens".** Honest saving vs `git log --grep`+LLM is ~3–5×; the big win is determinism + not saturating context.
12. **English by default** (OSS standard), Spanish via locale/`--lang`/`CHRONO_LANG`. JSON output never localized.
13. **Forge prefers `upstream`** on forks (PRs live upstream); drops heavy fields to avoid GitHub's GraphQL node limit; surfaces errors (no silent zero).
14. **Rust for the general core** *(2026-09-20, supersedes #9 for v2)*. The Go v0.1.1 binary stays the stable one until the Rust port reaches parity; the port lives in `rust/`. Rust buys parallel ingest with controlled memory for million-line traces and bit-stable integer JEV inference. Contract renamed to `entity`/`id` (`schema_version: 2`); v1→v2 migration is **reindex**, not in-place. See `DESIGN-GENERAL-CORE.md`.
15. **Log adapters (R3): jsonl, csv, textlog — zero external deps.** Each is an isolated crate implementing `Source`, registered in the CLI registry. `detect` is deliberately conservative so adapters never steal each other's files: csv is extension-gated to `.csv`/`.tsv` (never guesses CSV from content — a JSON line has commas too); textlog rejects any first line that matches no preset. textlog parses syslog (RFC5424/RFC3164) and nginx combined **by hand — no `regex` crate**, to keep the ~1.6 MB binary (Go was 6.7 MB). RFC3164 carries no year → taken from config `year`, else a fixed 1970 (deterministic, never the wall clock). A fourth adapter, **changelog** (Keep a Changelog), maps each version section to a `kind="release"` event and, unlike the append-only file adapters, uses a **content-hash watermark** (a changelog is edited at the top, so a byte offset is meaningless): same hash → nothing new, different hash → `Diverged` and the CLI re-ingests that source. Utilities (`simhash`, `timeutil`) are duplicated per adapter crate on purpose (crates stay independent), matching the jsonl precedent.
16. **Multi-source in one `.chrono/`** *(the real payoff of the general core)*. The `sources` table is populated per source, each with its own watermark; `chrono add <path>` ingests an extra source without wiping the index; `sync` iterates every source and reindexes only the one that diverged. On `sync`, git's forge/size refresh runs **only for git sources that actually re-ingested** (a log source getting new events no longer re-hits the GitHub API for an unchanged git source). `source_id = <kind>:<abs path>` — the same value events carry, so `correlate` and per-source queries line up. **Git parity is preserved** (verified on rustworkx + bun: hotspots top unchanged, init+sync idempotent, ~8s init at 17.7k commits). File-source divergence is caught two ways: the file gets **shorter** than the stored offset (truncation / rotate-to-smaller), **or** the hash of its consumed prefix changes. The prefix is the first `min(4096, off)` bytes (stored in the watermark as `off:<n>|p:<hex>`), hashed up to the offset — not up to the file length — so a plain append never falsely diverges, even on files under 4 KB. Honest limit of this heuristic: it only sees rewrites **within the first 4 KB**; an in-place edit past byte 4096 of an already-long file is not detected (the `4096` cap trades completeness for a cheap fixed-cost check). Old watermarks without `|p:` skip the hash check (backward-compatible). Second known limit: 2+ git repos in one index fight over the file-`deleted` flag (entities are global); the supported shape is 1 git + N log sources, whose entities aren't `type='file'`.

Determinism, precisely: two ingests of the same source produce **identical content** (events, touches, entities, labels, blob_lines — verified by dumping and hashing). The `.db` file is byte-for-byte identical **only when `now` is pinned** via the `CHRONO_NOW` env var (epoch seconds), because `sources.last_sync_at` records wall-clock time; without it the two files differ only in that one timestamp. The design's "hash the `.db` after VACUUM" reproducibility test must set `CHRONO_NOW`. (c) the git `bugs`/`hotspots` classifier still runs over log events, so those queries are only meaningful on a git-bearing index; `level` vocab isn't normalized across adapters (csv keeps the raw value upper-cased; syslog/nginx use the RFC severity names).

Per-source adapter options live in `.chrono/config.json` under `source_options` (keyed by the source's absolute path or its basename), e.g. `{"source_options": {"app.syslog": {"preset": "syslog", "year": "2024"}, "incidents.csv": {"time_column": "when", "delimiter": ";"}}}`. The CLI resolves them per source and passes them to the adapter's `open` (`Config::source_options_for`); with no entry, the adapter autodetects. This is what makes CSV column overrides and textlog `preset`/`year` reachable without code.
29. **schema v6: `rid` entero, `dims`, `at` derivado y `dim_rollups`** *(reindex avisado; fase 3 de `PLAN-FASES.md`)*. **(a)** `events.rid INTEGER PRIMARY KEY` (alias estable del rowid, como `sources.ref`) es la clave de `touches`, `labels` y `links`, ahora `WITHOUT ROWID`; `id` pasa a `UNIQUE` y sigue siendo lo que enseñan las salidas. **(b)** `at` es una columna virtual derivada de `at_epoch` con el formato que escribían los adaptadores (milisegundos solo si no son 0, `''` sin tiempo; comprobado: 0 diferencias en tres índices reales). **(c)** `dims` por fuente (`source_options`, o un preset): esas claves salen de `attrs` a `event_dims(dim_id, event_rid)` con el valor una vez en `dim_values(key, value)`; las fuentes glob llevan `file` como dim. `attr_keys(source_ref, key)` dice qué fuentes tienen cada clave en el JSON, así `top attr:k` y `--attr k:v` leen `event_dims` y solo el JSON de esas fuentes (con ninguna, 0 sin recorrer nada). Cambiar las dims de una fuente la reindexa en el siguiente `sync` (lo que salió de `attrs` no se recupera sin releer). `dim_id` es la clave de los joins entre fuentes de la fase 4. **(d)** `jsonl` deja fuera de `attrs` lo que ya es columna (tiempo, título, nivel, entidad, kind, ids); el actor se queda (suele ser el host). **(e)** Índices parciales: actor `WHERE actor_id IS NOT NULL`, bandas SimHash `WHERE kind = 'commit'` (`similar` recorre aparte los demás eventos, solo si los hay); sin `idx_events_kind`. **(f)** `dim_rollups` (fuente × plantilla × kind × nivel × nivel deducido × entidad × 10 min, mismo watermark y misma pasada que `rollups`) responde `top level|kind|entity`, `patterns`, `timeline` y `sources` con filtros de fuente, nivel, kind, entidad y ventana. **Exacto o nada:** con `grep`/`attr`, rollups atrasados, o un evento de varios touches (o un commit) en el alcance de una consulta por entidad, cae entero a `events`; una ventana que parte un bucket toma los buckets completos del cubo y los extremos de `events`. Un test compara cada consulta por los dos caminos con ventanas alineadas y sin alinear. Borrar eventos invalida el watermark. `rollups.source_id` pasa a `source_ref`. **Medido** (1M, `bench/escala/f3-0.5.0.json`): `.db` 584 → 321 MB, `informe` 10,7 → 0,6 s, `top attr:host` 1,04 → 0,02 s; sesiones de Claude 395 → 207 MB con las mismas cifras. Lo único que cambia en las salidas es el `example_id` de `patterns`: ahora el último evento ingerido de la plantilla (lo que ya decía su doc), no el mayor id en orden alfabético.
28. **Nod: fuente `nod` + `session_patterns` (proceso × resultado)** *(sin cambio de esquema: v5)*. `chrono add events.jsonl --as nod` (el `--as` genérico de la decisión 23; con sobres dentro `detect` da 90, por encima del 60 de `jsonl`) ingiere los sobres de Nod v1 de Claude Code y OpenCode (crate `chrono-source-nod`, aislado como el resto de adaptadores). id = `nod:<instance>:<run>:<seq>` (la identidad del contrato: dedup gratis por `INSERT OR IGNORE`), `kind = nod.<type>`, `at_epoch` = el `ts` de Nod tal cual (ya son ms, decisión 21), sin texto libre en el índice (ni prompts ni respuestas) y sin pasar por el clasificador de fixes. Relaciones como **links** para que las recorra `trace` (decisión 22): `vcs.commit` → `commit:<sha>` y `ticket:<tarea>`; `tool.result.links` → `url:<url>` (PRs, issues, artifacts) y `file:<ruta>`. El sha de `vcs.commit` suele venir abreviado, así que `trace` resuelve los links `commit` **por prefijo** (≥ 4 hex, rango sobre la PK de `events`, solo si casa con UN commit) en los dos sentidos: `chrono trace <sha>` da la sesión de Nod que lo creó. Esto sustituye al campo `linked` que una versión anterior añadía a `correlate`: `correlate` sigue siendo solo por tiempo. `session_patterns` cruza esos commits con hotspots (top N restringido a `file`), retrabajo a 30 días (líneas desde las columnas `added`/`deleted` de v5) y merge (ramas locales en vivo o PRs que citan la tarea). Definiciones, límites y ambigüedades del contrato en `docs/NOD.md`. Solo en Rust (decisión 14).
27. **schema v5: `source_ref` entero + columnas `added/deleted` en `touches`** *(reindex avisado; diseñado por un agente, implementado en serie, verificado contra el binario pre-v5)*. El `.db` pesaba ~1,1 KB/evento en parte por `events.source_id` TEXT (`"git:/abs/path"`, ~150 B repetidos por fila) y su `idx_events_src_at`. v5: **(a)** `sources` gana `ref INTEGER PRIMARY KEY` (alias estable del rowid — un rowid implícito lo renumera `VACUUM` y dejaría huérfanos; `id` pasa de PK a `UNIQUE` para conservar `ON CONFLICT(id)`); `events.source_id` TEXT → `source_ref INTEGER` (índice `idx_events_srcref_at`). El `Writer` resuelve el string→`ref` con caché y **auto-registra un stub** `INSERT OR IGNORE INTO sources(id,kind)` (el prefijo del id = kind), así el evento inserta su `source_ref` aunque `upsert_source` (que enriquece path/watermark) venga después — sin reordenar el CLI. `chrono_core::Event.source_id` y TODOS los adaptadores siguen emitiendo el string: no cambian. Solo 3 lectores de producción tocaban la columna (`events`, `correlate`, `trace`) → resuelven el string por `JOIN sources` (INNER, seguro: todo evento tiene `source_ref`); `--source` filtra sobre `s.id` (semántica idéntica) y `correlate` excluye la misma fuente por `source_ref` entero (biyección). `rollups`/`markers` quedan TEXT (diminutos; `patterns` no filtra por fuente) → menos blast radius. **(b)** `touches` gana `added`/`deleted` INTEGER (el `Writer` los parsea de `touch.attrs`, que git trae como string; binario = −1) y `churn` lee las columnas (`SUM(MAX(t.added,0))`) en vez de `json_extract` por fila. **Migración = reindex** (no in-place): `open()` da error claro si la versión no cuadra. **Medido:** `.db` de 285,6 → **181,5 MB (−36,5 %)** en un fixture de 300k (el ahorro sube con rutas de fuente largas). **Verificado byte-idéntico** al binario v4 en 17 consultas (git + jsonl, incl. `events --source`, `correlate` cruzando fuentes, `churn` desde columnas, `top`/`timeline`/`patterns`/`bugs`/`owners`/`coupling`/`similar`), determinismo (`.db` byte-idéntico con `CHRONO_NOW`; `ref` por orden de ingesta), sin eventos huérfanos (`LEFT JOIN sources` = 0), suite + clippy limpios. **Aún O(N) (futuro):** `top attr`/`entity`, `timeline --by` (necesitarían `dim_rollups` pre-agregado) y `similar` a dist ≥4 (bandas de 5×13 bits).
26. **Escala de consultas: índices aditivos + caminos sin O(N) (sin reindex)** *(implementado con 3 agentes en paralelo sobre módulos de metrics disjuntos; paridad verificada contra el binario pre-P3)*. Optimizaciones de las consultas que Fable midió como O(N), todas **aditivas y auto-aplicadas al abrir** (`CREATE … IF NOT EXISTS`): sin subir `schema_version` ni reindexar. **(a)** `hotspots`/`churn` ELIMINAN el JOIN a `events` cuando no hay ventana (`since==0`): ese JOIN solo servía para `at_epoch >= 0` y provocaba ~1M lookups aleatorios por la PK TEXT de `events` (Fable: 1,35 s→~0,1 s a 1M). Guard de paridad: el camino rápido se toma solo si `since==0` **y** no hay eventos con `at_epoch < 0` (import histórico pre-1970 → cae al JOIN, idéntico al actual), comprobado con `SELECT EXISTS(… at_epoch<0)` (covering `idx_events_at`, O(log N)). **(b)** `top level`/`top actor` usan índices covering nuevos `idx_events_level (level, at_epoch)` / `idx_events_actor (actor_id, at_epoch)` — el SQL genérico ya los engancha en cuanto existen (como `top kind` con `idx_events_kind`): sin `SCAN events`, SQL sin cambios (no arriesgar paridad). **(c)** `timeline` lee de `rollups` (O(#buckets)) en vez de escanear `events`, SOLO cuando es garantizado byte-idéntico: sin `--by`, `bucket_ms` múltiplo de `rollup_bucket_ms`, ventana alineada al bucket, y rollups al día (`meta.rollup_max_rowid == MAX(events.rowid)`); cualquier otro caso cae a `events`. Ambos caminos excluyen `at_epoch<=0` igual. **(d)** `similar` por **bandas SimHash**: el simhash de 64 bits se parte en 4 bandas de 16 bits (índices de expresión `idx_events_sh0..3`); dos valores a distancia Hamming ≤3 comparten ≥1 banda (pigeonhole), así que se recuperan candidatos por igualdad de banda (`MULTI-INDEX OR`, sin `SCAN events`) y se refina con Hamming exacto. `BAND_MAX_DIST=3`: para `max_dist ≥ 4` (el **default** de la CLI, que no expone `--max-dist`) cae al escaneo histórico para no perder recall → el default no acelera pero es byte-idéntico; las bandas ayudan a `max_dist ≤ 3`. **Verificado:** salida byte-idéntica al binario pre-P3 (`7f4910c`) en 14 consultas sobre jsonl (408 ev, incl. eventos sin tiempo y duplicados exactos) + 12 sobre un repo git (paridad git sagrada intacta), determinismo (`.db` byte-idéntico con `CHRONO_NOW`), suite completa + clippy limpios. Los `EXPLAIN QUERY PLAN` confirman que cada camino engancha su índice/rollup; a 500k las consultas ya son sub-0,1 s (el beneficio es asintótico, el régimen de millones que midió Fable). **Deferido a P4 (schema v5, un reindex):** `source_id`→entero, columnas `added/deleted` en `touches`, y `dim_rollups` para `top`/`timeline --by` a escala.
25. **Escala dinámica: ingesta por lotes + sync incremental O(delta)** *(sin sharding; analizado con un agente sobre un fixture de 1M y verificado a 2M)*. Para ser "dinámico a cualquier cantidad de eventos" sin partir la BD (el sharding rompería `correlate`/`trace`/`events`, que son el valor, y contradice el `.db` portable de la decisión 1), se quitaron los techos locales medidos: **(a) ingesta** — `foreign_keys=OFF` durante la ingesta (el `Writer` ya inserta el evento antes que sus touches/labels, así que la integridad está garantizada por orden), `cache_size=-262144` (256 MB), `temp_store=FILE` y `wal_autocheckpoint=10000`; **commits por lotes** de 100k eventos (`INGEST_BATCH`) con las cachés `actor.key→id`/`entity.key→id` preservadas entre lotes (`WriterCaches`/`writer_seeded`/`finish`), para no re-consultar ni perder la aceleración. **(b) VACUUM fuera del camino caliente** — a 1M copiaba el `.db` entero en RAM (OOM a 10M); `optimize()` ya no lo hace, es opt-in (`init --compact` → `Store::compact`). **(c) `sync` incremental** — `synced_any` solo si `n>0` o hubo divergencia (antes un sync vacío rehacía todo: 9,8 s → **6 ms**); FTS incremental (`fts_sync`: `INSERT … WHERE rowid > meta.fts_max_rowid`) y rollups incrementales (`build_rollups_sync`: agrega solo `rowid > meta.rollup_max_rowid` con `ON CONFLICT … count=count+excluded.count`), cayendo a reconstrucción completa (`rebuild_fts`/`build_rollups`) **solo** en `init`, re-ingesta (`add` de una fuente ya indexada) o divergencia, donde los rowids se reasignan. **(d) `ANALYZE` no en cada sync** — a 2M costaba ~15 s (O(N)); `optimize(full_analyze)` hace `ANALYZE` entero solo en reconstrucción (estadísticas deterministas → `.db` byte-reproducible) y `PRAGMA optimize` (barato, re-analiza solo tablas obsoletas) en el sync incremental. **Medido (M4, release):** curva de ingesta de 3× de caída (→13k ev/s) a ~1,3× (36,5k→31,8k ev/s a 2M); RSS de 1,7 GB/1M a **676 MB/2M** (sin OOM); sync vacío 9,8 s→6 ms; sync de +1000 sobre 2M 10,4 s→0,9 s. **Paridad/determinismo verificados:** `init` de una vez == `init`+`sync` partido (rollups byte-idénticos incluyendo `first_id`/`last_id`, + `patterns`/`timeline`/`top`/`search` idénticos); dos `init` → `.db` byte-idéntico con `CHRONO_NOW`; divergencia (edición in-place) reingiere y queda correcta sin doble conteo; paridad git intacta (hotspots/churn/events/patterns iguales entre full e incremental). **Aplazado (schema v5, un solo reindex):** `source_id`→entero (−25 % de `.db`, `idx_events_src_at` de 195→15 MB/1M), quitar el join a `events` en hotspots/churn cuando `since=0`, índices `(level,at_epoch)`/`(actor_id,at_epoch)`, `dim_rollups` para `top`/`timeline --by` a escala, y bandas SimHash para `similar` (decisión 19).
24. **jsonl con rutas anidadas + `explode` (una línea → N eventos)**. Los selectores de campo de jsonl aceptan RUTAS (`message.content[].name`, `data.0.id`), no solo claves de nivel superior; retrocompatible (un nombre sin `.`/`[]` resuelve como antes, incluidas claves con punto). `explode` (ruta a un array) emite un evento por elemento, con `explode_where` (`clave=valor`) para filtrar elementos, y resolución **elemento-luego-raíz** de los campos. ids únicos y deterministas por elemento. Habilita analizar transcripts de sesión Claude sin pre-procesar: `explode="message.content"` + `explode_where="type=tool_use"` + `entity_field="name"` → un evento por tool_use. Verificado sobre una sesión real: `top entity` da el desglose de herramientas (Bash 16, Write 3…) en microsegundos. Esto, con el adaptador `template`, hace a chrono analizable sobre casi cualquier contenido solo con config.
23. **Adaptadores definidos por config (sin Rust)** *(chrono agnóstico a quién lo usa)*. Para analizar "cualquier" contenido con tiempo basta `.chrono/config.json`, sin escribir un crate: (a) **jsonl/csv** ya mapean campos/columnas por config (`time_field`, `message_field`, `delimiter`…); (b) nuevo adaptador **`template`** para texto plano arbitrario: una plantilla de línea con marcadores `<time>/<level>/<service>/<message>/<actor>` y literales entre ellos (espacios flexibles, `<<` = `<` literal, captura no voraz), SIN la crate `regex` → binario sigue ~1,6 MB. Se elige con `chrono add <f> --as template` o con `"adapter": "template"` en las `source_options` de esa fuente (y entonces `chrono add` ya no necesita `--as`). El flag genérico `--as <kind>` fuerza cualquier adaptador. Verificado: un formato `TS | LEVEL | service | msg` definido solo en config se ingiere y consulta. Lo pesado (correlación, dedup de plantillas, respuestas deterministas en ms) lo pone chrono; el usuario solo describe el formato.
22. **`trace` (cadena causal) + `tail` (seguimiento en vivo)**. `chrono trace <id>` recorre el grafo de `links` (BFS acotado por `--depth`): dos eventos conectan si comparten un link `(rel,target)` (co-ticket/co-pr/revierten lo mismo → `rel="<rel>:<target>"`) o si uno referencia al otro por id (`reverts` → `rel="reverts"`), con inverso. Orden determinista (depth, at_epoch, id); empates de `rel` por menor lexicográfico. Complementa a `correlate` (que va por tiempo): trace va por relación explícita. Índice nuevo `idx_links_target` para la búsqueda inversa. `chrono tail [--interval 2s] [--source/--kind/--level/--grep]` sigue el índice como `tail -f`: cada intervalo ingiere el delta de cada fuente **sin el enriquecimiento pesado** (ni FTS, ni rollups, ni tamaños/forge — solo mete los eventos) e imprime los nuevos en orden cronológico (con resolución de ms). Bucle infinito, Ctrl-C para parar; pensado para fuentes que crecen (logs/oslog). Verificado: tail imprime appends a un jsonl en vivo con `.mmm`; trace enlaza co-ticket y reverts.
21. **Tiempo en MILISEGUNDOS + `events` (vista de trazabilidad)** *(schema_version 4, reindex)*. `at_epoch` pasa de segundos a **milisegundos** en todo el dominio: los adaptadores conservan la sub-segundo (RFC3339 `.fff`, micros de macOS/journald → ms; git/syslog/nginx son segundo → ×1000), `at` muestra `.mmm` solo cuando no es cero (git queda limpio), y las ventanas/buckets/`--bucket`/`--delta` son ms (`--bucket 500ms`). `CHRONO_NOW` sigue en segundos (×1000) por comodidad. Esto hace literal "trazable al milisegundo": eventos sub-segundo se ordenan y correlacionan bien. Nueva consulta **`chrono events`**: stream CRONOLÓGICO unificado de todas las fuentes (git+logs+deploys…), filtrable por `--source`/`--kind`/`--level`/`--grep` y ventana `--since`/`--until`, acotado (`--limit`, 100). Es la "trazabilidad en el tiempo" propiamente dicha. Verificado: eventos a +120/+250/+410 ms distinguibles en `events`; paridad git intacta (su `at` no lleva ms).
20. **`oslog`: log del sistema adaptable al SO.** `chrono add oslog` (token mágico, no un fichero) ingiere el log del sistema: en macOS via `log show --style json` (array JSON), en Linux via `journalctl -o json` (JSONL) — se elige por `cfg!(target_os)`. Ventana acotada (`options["window"]`, por defecto 5m: el volumen es enorme, ~24k registros en 2 min) + el cap global `max_events_per_source`. Watermark `since:<epoch>` para reanudar (`--start` en macOS con la limitación de zona horaria documentada; `--since @epoch` exacto en Linux). `detect` solo puntúa si el token casa Y la herramienta del SO existe. Verificado en macOS: `add oslog` trae eventos con `top level` (DEFAULT/ERROR/FAULT) y `top entity` = subsistemas reales (kernel, ApplicationFirewall…). Cursor buffered (acotado por la ventana).
19. **Escala: `bench` + caps declarados; bandas SimHash aplazadas (honesto).** `chrono bench` mide la latencia de cada consulta sobre el índice actual + estadísticas (eventos/entidades/`.db`) — sin reingerir. Caps de ingesta en `.chrono/config.json`: `body_max_bytes` (recorta el body) y `max_events_per_source` (corta la ingesta); **0 = sin cap por defecto** (preserva la paridad git) y, si >0, el efecto se DECLARA en `meta` (verificado). **Aplazado a propósito:** las bandas SimHash para `similar` a >1M eventos (el `similar` actual escanea, suficiente hasta ~1M) — construirlas sin un fixture de millones para verificarlas iría contra el listón; se harán con ese fixture. La paginación de `gh` ya la hace `gh --limit` internamente; el tope por tipo (1000) queda configurable como trabajo menor.
18. **Templates + rollups (`patterns`)** *(schema_version 3, reindex avisado)*. `chrono patterns` agrupa millones de líneas de log en unas pocas PLANTILLAS con normalización Drain-light determinista (`chrono_core::templatize`: valores → `<NUM>`/`<IP>`/`<HEX>`/`<UUID>`, sin `regex`, tokenización a mano). Se materializan en `templates` (plantilla única por fuente) y `rollups` (conteo por fuente×plantilla×bucket de 60 s), reconstruidos en `finalize` agregando EN MEMORIA por plantilla×bucket (acotado, no por nº de eventos). `patterns` lee de `rollups` (no escanea `events`) → escala. Verificado: 100k líneas → 5 plantillas en ~2,6 s; sobre git agrupa subjects (p.ej. commits de Dependabot). Coste: `finalize` rehace los rollups en cada `init`/`sync` (O(eventos), aceptable; el streaming incremental sería la mejora a escala real). El `<NUM>` es agresivo (p.ej. `pyo3`→`pyo<NUM>`): correcto para una plantilla, no para nombres.
17. **Log-native queries read raw events; rollups are a separate wave.** `timeline` (counts per time bucket, optional `--by level|kind`), `top <dim>` (`level`|`kind`|`actor`|`entity`|`attr:<key>`), `correlate <id>` (events from *other* sources within ±Δt) query `events`/`touches` directly — correct and fast at current scale, with fully-ordered deterministic output. All three are **bounded** (`--limit`, default 500 for `timeline`/`top`, 25 for `correlate`): `timeline` keeps the oldest buckets and reports `truncated` honestly; narrow with `--since`/`--until`/`--bucket`. Drain-light templates + the `templates`/`rollups`/`event_dims` tables (for million-line logs) are their own later wave with a real-log eval, like JEV — not codegen'd blind. `attr:` uses a bound `json_extract` path plus a `[A-Za-z0-9_.-]` key allowlist (no SQL injection).

## Deterministic classification (bugs/tickets)

Prose intent can't be made deterministic, but it can be made **reproducible and explicit**:
1. **Rules in `.chrono/config.json`** (versionable): `fix_keywords`, `ticket_patterns`, `exclude_globs`, `bug_labels`, `bug_categories`.
2. **Git-native signals** (100% deterministic): reverts via the `This reverts commit <sha>` body; conventional-commit prefixes.
3. **Forge labels** are the real ground truth for "is this a bug" — fires where the team labels/links PRs; requires the Tracker port (implemented).
